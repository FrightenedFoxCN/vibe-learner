### Interactive-question submission UX

- Each Turn has an independent local `submitting` / `failed` state.
- During submit, answer editing, duplicate submit, and “ask another question” are disabled.
- No local verdict is displayed or cached before persistence.
- Failure preserves the selected/typed answer and exposes an in-question retry without revealing a verdict.
- Success is displayed only after the returned Session advances revision and binds the same Session, Turn, submitted answer, boolean verdict, and non-empty feedback.
- Concurrent attempts on different Turns cannot roll the browser back: a late lower-revision response keeps the newer snapshot after confirming that it already contains the committed answer, a legitimate concurrent append-only Turn suffix is accepted, committed Turn-prefix drift fails closed, and a response for an inactive Session is not applied to the current view.
- Automatic continuation uses the committed question read-back and a Turn-scoped operation key rather than the optimistic browser verdict.
- The optional automatic callback runs after answer commit; callback failure does not roll back or visually downgrade the recorded answer.

The backend contract is deliberately not redesigned in this UX slice. Current known risks are fully tracked by `SCH-STUDY-QUESTION-001` and `SCH-STUDY-ATTEMPT-001`: answer material is exposed before submit, the endpoint locates a question by prompt, accepts client grading fields, and lacks Turn/revision/stable-attempt identity.
