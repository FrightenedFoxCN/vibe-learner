## 优先问题

### A01 · P1 · Study 切换章节形成重复写入循环（浏览器与日志确认）

无论带不带深链接参数，已有 Session 时切换至其他 Study Unit 都能触发大量重复 `PATCH /study-sessions/{id}`。首个带参数复现场景在 **45.199 秒内产生 7,135 个唯一 PATCH 请求**，其中 7,123 个 200、12 个 409，峰值 182 次/秒。同时自动开场操作出现 `study_chat_committed_session_revision_mismatch` 并进入 `uncertain`。发现后已离开触发视图；审计结束时关闭了本轮临时前后端服务。

普通 `/study` 对照场景在 **187.584 秒产生29,785次PATCH**（29,714×200、71×409，峰值186次/秒）。同一Session另外记录20,477次Chat POST，其中20,474次是409拒绝，不能称为模型调用；后续请求循环见A16。全部为本地mock环境。

`study-dialog-page.tsx:339` 的同步 effect 依赖每次 render 重新创建的 `handleSwitchSection`。控制器 `1496` 行函数先 dispatch busy，造成新 render；没有按 Session/目标 Unit 对在途请求去重。`1328` 行推进 view revision，`1364` 行又将较早响应判过期，导致状态持续不同步。

复现：创建含两个以上排期的计划 → 创建会话 → 从排期 1 选择排期 2 → 观察 Network 中连续 PATCH、更新态和失败提示。普通 `/study` 也已做对照复现，因此不能只修 URL 参数。

修复验收：同一目标仅一条在途更新；迟到响应不可覆盖新选择；请求数有确定上限；同步和自动开场互不制造修订冲突；真实浏览器在正常网速、慢网、快速往返切换下独立验收。

证据：`audit-2026-09-06-evidence/study-switch-loop-summary.json`、`study-switch-loop-ordinary-summary.json` 及对应日志摘录。

### A02 · P1 · 纯目标计划同步/流式接口必现 500（浏览器与独立 API 确认）

`services/ai/app/api/routes.py:2475`、`:2642` 创建 `goal-only:<uuid>` 标识。`local_store.py:35` 仅允许字母数字及点、下划线、横线；`StreamReportRecorder` 初始化便保存该 ID，触发 `local_store_item_id_unsafe`，模型和 operation admission 尚未开始。

复现：Plan Workspace 选“仅学习目标” → 输入目标 → “按目标生成”。页面提示 `Cannot reach AI service`；独立 TestClient 证明 `/learning-plans` 和 `/learning-plans/stream` 都返回 500。该提示无法反映实际业务错误。

修复验收：安全存储标识与领域 subject 分开；两接口在全新数据目录均成功；覆盖 stream 历史读回、失败终态和 goal-only Study 关联。

证据：`audit-2026-09-06-evidence/repro-goal-only.py`。

### A03 · P1 · Study 深链接持续强制原计划与排期（浏览器确认）

`apps/web/components/study-dialog-page.tsx:242` 和 `:247` 持续应用 URL 中的 plan/schedule，首次定位后不消费。由 Plan“开始”进入后，再切其他计划或排期，会立即被改回原选择。实际浏览器选择第二计划后仍显示原 Lyra 计划；三排期场景选择第二排期后又显示第一排期。

修复验收：URL 用于首次定位或显式导航变化；后续手工选择能够保持，完成章节后的自动前进也不能被旧 query 覆盖。该项与 A01 是两个不同原因。

### A04 · P1 · Wave 4 子阶段 trace 不能证明原执行成功（独立注入与代码确认）

`services/ai/app/services/harness_broad_adoption.py:559` 明确在已生成结果上创建子阶段证据；`:586` 从快照重新解码结果，未包住原解析/OCR/Planning Tool 执行。`:594` 读取 `outcome`，但 `:600` 固定写 PASSED，仅改变说明文案。

独立传入 `ocr_page / outcome=failed`，得到 `trace.status=passed`、`checks=[passed]`。这最多证明“结果证据形状被接受”，不能当作 OCR 执行成功、真实耗时或真实尝试次数。当前 stage 命名和 roadmap 完成声明扩大了证据含义。

修复验收：真实执行边界产生阶段记录；失败、不可用、无需执行、修复后完成分开；计时和尝试对应原调用；父终态遵守明确政策，不强求所有可降级子阶段成功，但必须如实记录。

### A05 · P1 · Tavern 替换名册破坏历史 Message 证据和后续互动（独立 API 确认）

`services/ai/app/persistence/tavern_repository.py:1324` 替换名单时删除旧 Participant 快照。历史 Message 仍存在，其提交读回却依赖当前名单。

独立临时库复现：A 生成成功 → PATCH 将 A 换成 B 返回 200 → 旧 Message 投影校验失败 `tavern_commit_persona_not_in_room` → Continue 以 A 的旧消息为锚、目标 B 时返回 500，Run 为 failed，错误 `tavern_commit_addressed_participant_not_in_room`。

完整名单管理尚非现有浏览器主入口，但 PATCH API 已公开。应保留被历史 Message/Run 引用的角色快照，或禁止破坏引用的变更。

证据：`audit-2026-09-06-evidence/tavern-roster-observations.md`；它是已执行结果的转录和步骤，原内联脚本未保存，不冒充原始日志。

### A06 · P1 · 桌面退出依赖 Drop，缺显式 sidecar 清理（代码与锁定依赖确认）

`apps/desktop/src-tauri/src/lib.rs:42` 仅在 `ManagedSidecar::drop` 中 kill/wait。`:444` 使用 Tauri `.run()`，未处理 `RunEvent::Exit`。锁定依赖 Tauri 2.10.3 的 run 文档与实现表明最终使用 `std::process::exit`，不能依赖普通 Rust 析构清理托管状态。

风险是正常退出后后端进程、端口和已解锁的会话状态残留。**未运行真实桌面安装包验证进程残留，因此保留动态验收缺口。** 应显式处理退出并验收完整子进程树、重启、异常退出与 Vault 锁定。

### A16 · P1 · 自动开场失败后存在无界再次提交（日志与代码路径支持）
